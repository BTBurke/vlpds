# Spaces on real R2

Run on 2026-10-05 from benchbox (Ryzen AI Max+ 395, wired 2.5 GbE, home network) to the
`vlpds-bench` R2 bucket in wnam. vlpds is `origin/spaces-2c` 8346b200, built with `--release`.
The PLC and the reference PDSes ran locally in docker, as in every harness run. Only vlpds's bucket
moved. Every run was alone on benchbox, between batch pipeline windows, with both build lanes paused.

The harness option is `STORE=r2` (bench/spaces/README.md, "Real R2"). Each run gets its own
`bench/<run-id>/` prefix, which `r2-clean.sh` deletes afterwards. The single node ran with
`--shards 16` (the default is 64), since every shard polls and checkpoints on its own and R2 bills
idle requests. The cluster runs 16 shards over 3 nodes anyway. On R2 the cluster also runs with the
vlpds default `--lease-ttl-ms 10000`, where the harness uses 3000 on MinIO (see "Surprises").

The comparison columns come from different builds, and that's worth keeping in mind:

- MinIO is the Mac harness on loopback MinIO, dev-release profile. The cost run is `spaces-1`
  ba503d00 and boards is `spaces-2a` 64ce2efd at full scale (20 members, 4,200 writes).
- Modeled S3 is the in-process micro-bench in `spaces-sync.md` (`spaces-1` 3ebf852d on benchbox),
  with segment PUTs delayed 25 ms median.

Release against dev-release doesn't matter much here. On R2 a write spends ~214 ms in the segment
PUT and well under 1 ms everywhere else in the commit path.

## Raw R2 latency

`vlpds-bucket-probe --ops 30 --concurrency 1` (the node's own S3 client, so the same pool, timeouts
and path-style requests). Every correctness check passed (conditional create, CAS on ETag, the
one-winner races, list/read/delete, multipart), so R2 is safe for vlpds.

| op | benchbox p50 | p90 | p99 (= max at n 30) |
|---|---|---|---|
| put_create 64 KiB (a segment PUT) | 202.8 ms | 296.4 ms | 379.6 ms |
| put_cas 200 B (a lease renewal) | 206.3 ms | 239.6 ms | 320.8 ms |
| put 64 KiB | 197.2 ms | 299.3 ms | 518.4 ms |
| put 1 MiB | 227.6 ms | 338.2 ms | 763.4 ms |
| get 1 KiB | 57.4 ms | 116.5 ms | 403.2 ms |
| get range 4 KiB | 80.1 ms | 147.1 ms | 445.4 ms |
| head | 59.8 ms | 99.0 ms | 452.4 ms |
| list | 70.0 ms | 95.1 ms | 157.4 ms |
| delete | 111.6 ms | 169.3 ms | 399.6 ms |

The network isn't where that time goes. From benchbox, a TCP connect to the R2 endpoint takes
1-2 ms and the TLS handshake ~17 ms, and an unauthenticated request comes back in ~35 ms. So a
Cloudflare edge is close, and a write spends ~180 ms behind it on R2's storage path. A GET is
~60 ms. Every number below follows from the ~200 ms PUT.

(The Mac on Wi-Fi measured put_create 244.5 / 473.1 ms and get 73.8 / 164.2 ms p50 / p99, about
40 ms more per PUT. The Mac numbers are a footnote only, and none of the runs below used it.)

The no-op poll and delta pull rows don't touch the bucket, so R2 changes nothing there. The R2
column is ~2x the MinIO one because benchbox was a different machine with a different build, and the
whole thing is well under the 1 ms and few-ms targets either way.

A space write's latency is one R2 PUT. Over the 300 warm writes, `commit_durable` averaged
214.3 ms, the PUT stage 213.5 ms, and seal_wait, apply_lock, apply and ack added 0.5 ms between
them. Server time per write averaged 215-218 ms, so the HTTP and OAuth path adds ~2 ms, and the
client sees ~200 ms p50 (the server histogram's buckets are coarse at 204.8 and 409.6 ms).

Notify costs one more durable entry (the authority's `sW`/`sQ` entry), so it lands one PUT after
the write is readable (218.6 ms p50). The modeled number is two PUTs in a row (write and then the
authority's entry, at 25 ms each, plus queueing).

With 4 writers in flight, a public commit's p50 is ~1.5 PUTs (304.5 ms). A write that arrives
while a segment PUT is in flight waits for it, then goes out in the next one. A space write load
next to it moved public p50 by 43 ms and p99 not at all (643.3 → 629.9 ms). The check passed.

Three checks failed, and none of them points at the Spaces write path:

- `noop-poll` saw 2 bucket ops during its 221 ms window (one lease CAS and one GC-boundary read).
  Those are background requests that happened to fall in the window, and the polls didn't cause
  them.
- `notify-latency` targets p50 under 100 ms "locally". One R2 PUT is 200 ms, so it can't pass on
  R2 and doesn't say anything about linger.
- `bucket-ops` compares all bucket ops per write (2.53 space against 1.90 public). Segment PUTs
  per write were the same (364 and 372 over 300 writes each). The difference is in compaction
  polls and GC-boundary reads (168 and 267 GETs against 66 and 156), and those are time-based
  background requests. A step that ends with more L0 to compact switches the compactor to its
  500 ms polls.

Segment PUTs per write came out above 1, and the reason isn't confirmed. One likely source is
the checkpoints (16 shards every 10 s, each writing an applied marker to the log), which add ~0.3
segments per write over a 60 s step at this write rate.

The 12 bucket ops per warm write is the same thing at a slower write rate. One writer at 4.6
writes/s pays a segment PUT per write, and the checkpoint flushes, manifest reads and compaction
polls go on at ~50 requests/s whatever the write rate is. Per write they look expensive only
because the writes are slow.

## Boards, all-vlpds, single node

`SCALE=r2` (10 members, 80 posts, 300 comments, 800 votes in story 10, 16 in flight). Every story
passed, including the restart with `--lexicon-authority-override` and the bare-grant consent
flow.

| measurement | MinIO (Mac, full scale) | R2 (benchbox, r2 scale) |
|---|---|---|
| write ack → visible on the appview (notify-driven) p50 / p99 | 11.2 / 25.0 ms | 224.4 / 317.1 ms |
| takedown → appview converged | 1,903 ms | 714 ms |
| revoke → reads refused | 9 ms | 225 ms |
| story 10 throughput (16 in flight) | 1,996 writes/s | 20.9 writes/s (1,180 in 56.5 s) |
| appview caught up after the last ack | 17 ms | 15 ms |
| bucket ops per write in story 10 | 0.53 | 1.98 |
| acked writes lost | 0 | 0 |

Ack to visible is one PUT (the authority's entry before the notify) plus a pull from the appview,
so it's ~one R2 PUT more than the write itself. Revoke is one durable write. Takedown converged on
the appview's 2 s poll here, since this run (spaces-2c) didn't push a record takedown, so it's
anywhere from 0 to 2 s plus a pull on either store. spaces-2b pushes takedowns and reversals since
(the author resends the served hash at the same rev, and the authority checks it against the
writer's signed commit, at most 3 checks per writer and space per 10 minutes), so the appview
should converge in about one notify and one pull instead.

At 16 in flight the board took ~21 writes/s, so each write took ~760 ms (~3.7 PUTs). One PUT is
in flight per segment, and each write waits behind the one in flight before its own goes out. 16
writers spread over 10 repos also queue behind their own repo's previous write. This run doesn't break
that down further. The MinIO number is ~100x higher, and the gap is close to the PUT latency
ratio.

## Boards, all-vlpds, 3-node cluster with a kill -9

`CLUSTER=1 SCALE=r2`. Story 11 sends node 1 `kill -9` 30% into story 10 and keeps it down 20 s.
Every story passed.

| measurement | MinIO (Mac, full scale, 3 s lease TTL) | R2 (benchbox, r2 scale, 10 s lease TTL) |
|---|---|---|
| write ack → visible p50 / p99 | 10.8 / 20.7 ms | 249.1 / 412.4 ms |
| takedown → appview | 1,885 ms | 27 ms |
| revoke → refused | 15 ms | 448 ms |
| story 10 throughput | 807 writes/s | 19.1 writes/s (1,164 acked in 60.9 s) |
| n1 down (kill → restarted and settled) | 20.7 s | 32.0 s |
| acked while n1 was down | 2,954 | 468 |
| uncertain writes (in flight at the kill) | 1 | 16 |
| acked writes lost | 0 | 0 |
| listRepos at every writer's head after failover | yes | yes |

The failover from the node logs:

| after the kill | what happened |
|---|---|
| 3.7 s | n0 and n2 both see n1 miss a renewal and refuse connections |
| 4.7 s | both fence n1's log (ordinal 277) |
| 4.9-5.1 s | n0 takes shards 10-11 and n2 takes 12-13 |
| 9.1-9.8 s | n1's log drained to its fence on both nodes |
| 10.0 s | n2 takes shards 14-15, so all of n1's shards have an owner |
| 20 s | the harness restarts n1, which is ready 2.1 s later with no shards |
| 25-29 s | n0 hands shards back, and n1 adopts 8-9 and 4-5 |
| 32 s | the harness sees the cluster settled |

So writes to n1's shards waited ~5 s for their first new owner and up to ~10 s for the last pair.
The 16 uncertain writes were in flight at the kill, which is more than MinIO's 1 because at 200 ms
a PUT holds more writes in flight. The invariant checks counted them as uncertain, and every acked
write was on its host afterwards. The extra 12 s of "down" over MinIO is the restart and rebalance
at R2 speed (opening shards and handing them back), and boards kept taking writes the whole time.

## Surprises

- R2 PUTs take ~200 ms from a wired host near the edge, and GETs ~60 ms. The 25 ms the in-process
  bench models (S3 Standard) is 8x too optimistic for R2. Anything on R2 should expect ~200 ms
  acks for a lone writer and ~4-5 sequential writes/s per repo.
- The tail is wide. A 1 MiB PUT reached 763 ms and GET or HEAD reached 400-450 ms at only 30
  samples. One control-plane GET at cluster start took over 3 s, so n2 hit the harness's
  `--lease-ttl-ms 3000` (whose control-plane deadline is min(TTL, 5 s)) and exited with
  `control-plane get timed out after 3s`. A node fails its start instead of retrying there. The
  rerun at the default 10 s TTL had no timeouts.
- R2 answered 429 Too Many Requests twice in the cluster run, once when the nodes restarted for
  the lexicon override and once during shutdown after the run. Both were retried once after 100
  ms by object_store, and nothing above it noticed. That fits R2's limit of about one write a
  second to one key (lease and assignment objects get CAS'd by several nodes at once), but which key it was isn't confirmed.
- No 5xx, no other retries, and no timeouts outside that one start.
- Idle cost is mostly shards. The MinIO single node at 64 shards made 73 requests/s idle, and at
  16 shards on R2 it made ~10/s. A slow writer makes the background polls show up per write (12
  ops per warm write).

## Harness changes

- `STORE=r2` in `run.sh`, `lib/env.mjs` and `lib/vlpds.mjs`. The keys go to vlpds only through its
  environment. No log, report or JSON from these runs contains the key id or the secret (checked
  with grep against the env file).
- A request watchdog in `lib/vlpds.mjs` writes `out/r2-ops.json` and kills vlpds past
  `R2_OPS_LIMIT` (45,000).
- The driver now kills every vlpds node it started when it exits. Before this, a node that failed
  its start left the other two running (cluster start 2 above, ~1 minute against R2 until they were killed by hand).
- `r2-clean.sh` deletes a run's prefix with the aws CLI. benchbox has no aws CLI, so cleanup ran from
  the Mac.
- `SCALE=r2` in boards (10 / 80 / 300 / 800).
- On Linux, the reference PDS containers can't reach host ports bound to 127.0.0.1, so configs
  where a reference PDS talks to vlpds need Docker Desktop (the Mac) for now. That's why the R2
  runs are all-vlpds only.

The run outputs (reports, vlpds logs, probe JSON) are on benchbox in
`~/vlpds-bench/spaces-r2/results/`.
